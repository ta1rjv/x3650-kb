IMM Guide

The first-generation Integrated Management Module end to end - hardware and firmware internals, every interface (web, CLI, IPMI, SOL, SNMP, CIM/WS-Man, SLP, LAN over USB), users, Standard versus Premium, banks and recovery.

The Integrated Management Module (IMM) is the service processor of the x3650 M3. It is the first IMM generation ("IMM v1"); the x3650 M4 and later use IMM2 and XClarity Controller, which behave differently. This guide walks through the IMM from silicon to user interfaces. Authoritative detail: IMM architecture, IMM interfaces and the IMM web API.

What the IMM is #

Aspect Fact Level Where

SoC Big-endian MIPS32; kernel and drivers named vsc452, so the VSC452 is CANDIDATE as the SoC EXTRACTED / CANDIDATE IMM architecture 3.1
Operating system Embedded Linux 2.6.16.46, U-Boot 1.1.4, JFFS2 root and boot file systems, BusyBox, lighttpd 1.4.13, OpenSSH 4.2p1, net-snmp, OpenSLP, SFCB (CIM) EXTRACTED (IMM 1.10 and 1.55 images) IMM architecture 3.1
Web UI lineage 106 of 129 static web files carry an American Megatrends 2007-2008 copyright; derivation from the AMI MegaRAC stack is CANDIDATE EXTRACTED / CANDIDATE IMM web API 2.1
Boot time The IMM needs up to 17 minutes to be ready after a firmware update (up to 20 for the first restart); the power button becomes active about 2-3 minutes after AC is applied (sources differ) DOCUMENTED (S-022, S-020, S-002) IMM architecture 3.3
Heartbeat IMM heartbeat LED flashes fast while code loads, slowly when operational; not flashing within 30 s of AC means an IMM problem DOCUMENTED (S-004) IMM architecture 3.3

The IMM also holds part of the UEFI configuration: UEFI settings live in two tiers, NVRAM variables and an XML-modelled store kept by the IMM, which is what ASU reads and writes (S-024 p.15, S-025) (IMM architecture 3.2).

Port numbers can be changed on the Port Assignments page; on IMM1 a network-protocol change takes effect only after an IMM restart (S-020 pp.43-50, S-027 IMM1 notes). The ability to enable or disable every service port arrived in 1.32 (IMM interfaces 12).

Web interface #

After login the IMM v1 web interface offers (S-020 Table 2): System Status, Virtual Light Path, Event Log, Vital Product Data, Power/Restart, Remote Control (Premium), PXE Network Boot, Firmware Update, System Settings, Login Profiles, Alerts, Serial Port, Port Assignments, Network Interfaces, Network Protocols, Security, Configuration File, Restore Default Settings, Restart IMM, and on some systems Scalable Partitioning and Service Advisor (CANDIDATE: not applicable to the x3650 M3). Each link with its CLI and ASU equivalent is mapped in IMM interfaces 3.2.

On IMM1 the HTTPS server is disabled by default and no certificate exists until one is generated or imported; enabling HTTPS needs a certificate and an IMM restart (DOCUMENTED, S-020 pp.84-90, S-027 Appendix I). Cryptography mode "High Security" disables SSL and weak keys.

The 1.30 web client is analysed file by file in the IMM web API volume: the login is a POST /session/create, after which six WSDLs are downloaded and every WSDL operation becomes a JavaScript function. The six WS-Man services are Monitors (17 operations), Tasks (20), iBMCControl (54), iBMCNWProtocol (13), ServiceAdvisor (21) and Scalability (8); 53 are read operations by name (EXTRACTED, classification CANDIDATE).

Legacy CLI #

Commands present in the 1.30 help (MEASURED): ?, clearcfg, clearlog, clock, console, dhcpinfo, dns, exit, fans, gprofile, help, history, identify, ifconfig, ipsec, ldap, ntp, passwordcfg, portcfg, power, readlog, reset, resetsp, slp, srcfg, ssl, syshealth, temps, timeouts, update, usbeth, users, volts, vpd. Some commands documented in S-020 (for example portcontrol) belong to later firmware. Display forms are read-only; forms with options change state; clearlog, clearcfg, reset, resetsp, power and update change state (IMM interfaces 4.2, 4.3).

IPMI #

The IMM implements IPMI 2.0 with manufacturer ID 2 (IBM) and product ID 220; it supports the sensor device, SDR repository, SEL, FRU inventory, IPMB event receiver/generator and chassis functions; mc getsysinfo and DCMI discovery are not implemented (MEASURED on the reference unit). Authority levels map to IPMI privileges: Supervisor to Administrator, Read Only to User (DOCUMENTED, S-020 pp.35-36). IBM OEM commands exist but are not documented in the local sources (IMM interfaces 5.5). The sensor repository is decoded in Sensors and SDR.

Serial over LAN and serial redirection #

On rack System x servers COM1 carries IPMI Serial over LAN and is configured only through IPMI; COM2 is the internal port for serial redirection through the CLI (console 1); both are 8N1 at 9600-230400 baud. The rear serial port is shared with the IMM (DOCUMENTED, S-020 pp.16, 41; S-002). The UEFI side needs console redirection enabled (uEFI.RemoteConsoleRedirection, uEFI.SerialPortSharing, uEFI.SPRedirection and the COM settings); see the UEFI guide.

LAN over USB #

The IMM presents an internal Ethernet device (USB 04b3:4010 "IBM RNDIS/CDC ETHER") to the host. The IMM side is 169.254.95.118/16 (S-020 p.129); the documented Linux host address is 169.254.95.130 in S-020 and 169.254.95.120 in IBM's cdc_interface.sh (recorded conflict). From IMM 1.15 a DHCP server on the link is documented. ASU, DSA, UXSPI, BoMC media and the iflash packages use this link; they may reconfigure the host's network to do so, which IBM's own readmes warn can disturb cluster software. Disabling "commands on USB interface" stops in-band flash and ASU over this path (ASU can still use KCS) and should be paired with disabling the OS watchdogs (IMM architecture 4.2, IMM interfaces 10).

Users and authentication #

  • Up to 12 login profiles shared by web, CLI, SNMPv3 and IPMI; IPMI user ID 1 is the null user, IPMI ID n+1 is login ID n; login IDs at most 16 characters (DOCUMENTED, S-020 pp.33-38).
  • Authority levels: Supervisor, Read Only, Custom (with rights such as User Account Management, Remote Console, Remote Power/Restart, Clear Event Logs, Adapter Configuration Basic/Advanced, Networking and Security).
  • Login order options: local only, LDAP only, local first then LDAP, LDAP first then local. IPMI never uses LDAP.
  • Account security levels Legacy, High and Custom control lockout, web inactivity timeout, password history and age.
  • Factory defaults (DOCUMENTED in IBM readmes and S-020): login ID USERID with password PASSW0RD (zero, not the letter O); if no DHCP answer is received, the IMM uses the static address 192.168.70.125. Changing the default credentials is the first step of any deployment.
  • Password-rule details differ between sources (recorded conflict, IMM architecture 6).

Standard versus Premium #

Standard IMM includes remote power control, serial redirection, SOL, LAN over USB, LDAP, SNMP, ASU, remote firmware update, OS watchdogs and embedded DSA. Premium (the IBM Virtual Media Key, option 46C7526, FRU 46C7528, installed in a dedicated system-board slot with AC removed) adds remote presence (graphical KVM), operating-system failure screen capture and remote disk. No firmware change is needed for the upgrade (DOCUMENTED, S-020 pp.11-13, 114; S-001 Table 18). Remote presence supports up to 1280x1024 at 75 Hz per S-001 and S-020, 1600x1200 per S-002 and S-004 (recorded conflict). The 1.30 Remote Control page asks the IMM for a license status before showing the KVM launcher (EXTRACTED) (IMM architecture 7).

Event logging #

The IMM keeps two logs: the IPMI SEL (all BMC, POST and SMI events; fixed size; when full, new entries are not written) and the IMM event log (a filtered subset of IMM, POST and SMI events as text messages with event ids, plus IMM-internal events such as logins and network changes). The CLI readlog shows five entries per call, newest first; the web Event Log page sorts and filters; clearlog clears. An IMM reported its event log capacity as 1500 records through CIM (MEASURED on the reference unit). Decoding is covered in the troubleshooting guide (IMM architecture 10).

Firmware, banks and recovery #

  • Two banks. Primary and backup (secondary) IMM firmware pages; jumper J147 pins 1-2 normal, 2-3 boot the backup page; change only with power removed (DOCUMENTED, S-004 Table 4).
  • On flash (EXTRACTED, IMM 1.10): NAND managed by UBI with two sides (kernel volumes 1/2, rootfs 3/4, bootfs 7/8); U-Boot at offset 0 of an SPI flash selects the side via an environment variable and can fall back to TFTP; updates write the inactive side and a mirror job later copies the running side. How J147 maps to this is UNKNOWN (IMM architecture 3.2).
  • Automatic failover to the backup bank on corruption exists from IMM 1.40 (DOCUMENTED, changelog).
  • Event ids: 40000023/40000024 flash success/failure, 4000002a firmware mismatch, 806f052b-2101xxxx IMM firmware failover (DOCUMENTED, S-004).
  • Resetting: Setup -> System Settings -> Integrated Management Module offers "Reset IMM to Defaults" and "Reset IMM" (about 4 minutes); removing AC for 45 s resets the IMM (DSA I2C test note). Configuration backups exclude the Security page settings and the SSH server key (DOCUMENTED, S-020).
  • Known defect band: IMM 1.30-1.32 can fail over unexpectedly and stop (RETAIN H206034, fixed in 1.33); see the firmware guide.

Watchdogs and host integration #

The IMM offers an OS watchdog and a loader watchdog (server timeouts) that require the in-band USB interface; a missed check restarts the server. A POST watchdog (disabled by default) is configured in UEFI Setup. When no IBM in-band agent runs in the OS, the IMM may keep showing the server state "Booting OS" (S-020 p.111 lists "Booting OS or in unsupported OS"); on the reference unit this state is MEASURED while the OS runs, the cause is CANDIDATE (IMM architecture 4.5).

Open questions #

Still UNKNOWN in the volumes: which IMM bank is active and what level the backup holds (no read-only query known), the exact flash part numbers, the IBM OEM IPMI command set, the wire protocol ASU uses out-of-band to an IMM1, and the SoC identity beyond the PCI ID (IMM architecture 13).
