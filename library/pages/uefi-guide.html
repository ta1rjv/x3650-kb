UEFI Guide

The x3650 M3 system firmware - POST flow, the F1 Setup tree, ASU setting names, operating modes, console redirection, flash banks and recovery jumpers, microcode and what changed between releases.

The x3650 M3 was among IBM's early UEFI servers: its system firmware is UEFI 2.1 compliant, keeps a legacy BIOS compatibility module for older operating systems and adapters, and shares its configuration with the IMM. This guide summarises the UEFI volume; package and image formats are in the firmware guide and Firmware formats 6.

Architecture and POST flow #

DOCUMENTED (S-024, IBM's "Introducing uEFI-Compliant Firmware" paper) unless noted (UEFI 2):

  1. IMM initialisation and power sequencing. The IMM must be up before the host can start; this is why the power button only works some minutes after AC is applied.
  2. Platform initialisation (SEC and PEI phases): CPU, QPI and memory initialisation. The early code is the Capsule_P.scap image of the flash package (EXTRACTED).
  3. Pre-boot DXE: drivers, option ROMs, the Setup engine (FvDxe.fv, FvPlatform.fv, EXTRACTED).
  4. BDS (boot device selection): UEFI boot entries or legacy boot through the CSM (LegacyBios module, EXTRACTED).

Configuration lives in two tiers: UEFI NVRAM variables, and an XML-modelled store held by the IMM that ASU uses for every setting (S-024 p.15). Adapters present their configuration through HII forms (S-024 p.16).

RAS features of the firmware (S-024 pp.17-18): a locked CRTM region (a CRTM update is staged and applied at the next boot; the resulting power-good reset is expected), firmware volume integrity checks, a power-sequence watchdog, a POST watchdog (off by default), dual banks with automatic bank recovery, and a recovery behaviour after three consecutive boot failures. The update capsule carries an RSA2048-SHA256 signature trailer (EXTRACTED); POST codes 3818005-3818007 report invalid CRTM capsule signatures (DOCUMENTED, S-004).

Boot progress is reported as checkpoint codes on the light path panel display: 0x00-0x0F CPU init, 0x10-0x1F PEI, 0x20-0x9E DXE, 0x9F POST complete, 0xA0-0xAF QPI, 0xB0-0xBF memory, 0xE8 no memory, 0xEE invalid DIMM population (S-024 pp.27-28; a per-code table for this server is UNKNOWN) (Error codes 7).

Secure Boot is not supported: on the reference unit no Secure Boot variables exist and mokutil reports no support (MEASURED, UEFI 12.2).

Setup utility (F1) #

Press F1 at the prompt. With an administrator password set, entering it gives the full menu; otherwise a limited menu is shown (DOCUMENTED, S-002 pp.158-162). The tree (UEFI 4):

  • System Information: System Summary, Product Data (and, from the extracted forms, Reference Code Level and Processor Details Summary).
  • System Settings: Processors, Memory, Devices and I/O Ports, Power, Operating Modes, Legacy Support, Integrated Management Module (POST watchdog, Reboot System on NMI, Commands on USB Interface Preference, Network Configuration, Reset IMM to Defaults, Reset IMM), Adapters and UEFI Drivers, Network, Storage, Video.
  • Date and Time, Start Options, Boot Manager (boot order, driver options, one-time boot, WOL boot options, time-out, console options, COM attributes), System Event Logs (POST Event Viewer, System Event Log, clear), User Security (power-on and administrator passwords), Save Settings, Restore Settings, Load Default Settings, Exit Setup.

The extracted HII forms of 1.22 contain 27 formsets; the platform module alone renders about 1478 lines of options. Highlights per page (EXTRACTED, UEFI 5):

ASU setting names #

Every Setup option that has an ASU name can be read and written from the OS or over the network with the Advanced Settings Utility (see the tools guide). The setting list comes from an XML document inside FvOem_Ibm.fv: in UEFI 1.22 it defines 209 top-level settings (202 uEFI.*, 4 iSCSI.*, 3 PXE.*) and 147 sub-settings; the ASU name is <config mriName>.<setting mriName>, not the XML ID attribute (EXTRACTED; naming rule DOCUMENTED by S-026) (UEFI 7; the full table is UEFI Appendix A).

Two default conflicts are recorded: the C-state limit default (form versus XML) and the 1.14 CPU C-state default (UEFI 10). IMM settings use the IMM. prefix and are listed in IMM interfaces 11.

Operating modes #

The Operating Modes page sets several parameters at once (EXTRACTED; the mode-to-column assignment is CANDIDATE because the tool does not render the IFR OR operators) (UEFI 6):

Parameter Acoustic Efficiency Performance Custom (default)
Memory speed Minimal Power Power Efficiency Max Performance selectable (Max Performance)
Processor performance states Enabled Enabled Disabled selectable (Enabled)
C1 Enhanced mode Enabled Enabled Disabled selectable (Enabled)
QPI link speed Minimal Power Minimal Power Max Performance selectable (Max Performance)
Turbo mode Disabled Disabled Enabled selectable (Disabled)

Help text: "Efficiency: Highest performance per watt. Acoustic: Lower acoustic level and lowest power. Performance: Highest performance. Custom: Customized settings." A non-Custom mode makes the individual questions read-only. The thermal and power effect is discussed in Power and thermal 9.

Serial console redirection #

To see POST, Setup and the boot manager over IPMI Serial over LAN or the IMM CLI console 1, IBM's ASU example for IMM servers enables uEFI.RemoteConsoleRedirection, uEFI.SerialPortSharing, uEFI.SerialPortAccessMode (Dedicated; RETAIN H205981 warns that a session is lost after an IMM reset in Shared mode), uEFI.SPRedirection, VT100 terminal emulation and "active after boot" on the COM ports (DOCUMENTED, S-025). All of these default to Disable / ANSI in 1.22 (EXTRACTED). On rack servers COM1 carries SOL and COM2 serves CLI redirection (DOCUMENTED, S-020). After such a change on the reference unit the ConIn/ConOut NVRAM variables listed both UARTs at 115200 8N1 VT100 (MEASURED); serial output during POST itself was NOT VERIFIED (UEFI 12.3). The system summary is always shown on text remote consoles regardless of Quiet Boot (S-024).

Banks, recovery and jumpers #

  • Two banks. The UEFI flash has a primary and a backup bank (DOCUMENTED, S-004 p.372). SMBIOS OEM strings report the current bank and the backup level ("$CF Current UEFI Flash Bank", MEASURED on the reference unit).
  • Restoring the primary after a bad update: update the primary bank, boot once from the backup, then switch back by removing AC for 15 seconds or pressing F3 at the splash screen (S-024 p.18; S-004 p.372).
  • Jumper J29 (UEFI boot recovery): pins 1-2 normal, 2-3 load the backup page; change only with power off. Adapters on riser 2 may have to be removed to reach it (S-004 pp.372-373).
  • Automatic boot failure recovery (ABR): POST 3048006 = booted the backup image because of ABR; 3048005 = the backup switch was used.
  • Nx boot failure: after 3, 6 or 9 failed POST attempts (Setup -> Operating Modes -> POST Attempts Limit) the firmware loads defaults and enters Setup (POST 3058004, 3108007).
  • Clear CMOS: switch SW3-1 (power off, cover removed) resets UEFI settings (Hardware 4).
  • Backup-bank flashing: iflash --backup; RETAIN H196209 warns that updating the UEFI backup with the IMM32F method may fail (UEFI 3).

Microcode #

Each UEFI image carries six Intel microcode updates (Nehalem-EP 0x106A4/0x106A5 and Westmere-EP 0x206C0/1/2). For the common Westmere-EP stepping 0x206C2: 1.13 ships revision 0x14, 1.14 ships 0x15 (2011-08-26), 1.22 ships 0x1F (2018-05-08); the Spectre v2 and SSB mitigations arrived with 1.21 and 1.22 (EXTRACTED / DOCUMENTED). An OS can also load newer microcode at boot without flashing (discussed in Optimization 10.4) (UEFI 9).

Open questions #

The meaning of the protected="true" attribute on 134 settings, the per-code checkpoint table, the exact mapping of the IMM-side settings store and some form-to-XML mappings remain UNKNOWN (UEFI 11).
