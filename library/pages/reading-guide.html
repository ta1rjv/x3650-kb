Reading Guide

How to read the library - truth levels with examples, source ids, page conventions, how measurements and firmware analysis were done, and the limits of the evidence.

The library is written so that every statement can be traced back to evidence. This page explains the labels you will meet on every page, how the evidence was produced, and what the evidence cannot tell you.

Truth levels #

The levels are defined in docs/AGENT.md of the repository and used identically in every volume. A table row inherits the level stated for its table; a sentence states its own.

Level What it means Typical evidence Example from the library
DOCUMENTED A vendor document says so. Guide title, edition, source id S-xxx and page or section. "This server does not use beep codes for server status" (S-004 printed p.274), Error codes 8.
EXTRACTED Read from a vendor firmware binary or package by offline analysis. Package path, SHA256, offset or member name, tool command. UEFI 1.22 ships microcode revision 0x1F for CPUID 0x206C2, UEFI 9.
MEASURED Captured from the reference unit with a read-only command; the raw output is kept under captures/. Capture file and line. The reference unit reports IPMI version 2.0, manufacturer ID 2 (IBM), product ID 220, IMM architecture 2.
CANDIDATE An inference that is plausible but not proven; the reason is always written next to it. Reasoning from other facts. The IMM SoC is the Vitesse VSC452 (reason: PCI ID plus driver names in the firmware), IMM architecture 3.1.
UNKNOWN No source in the repository establishes it. - Which IMM flash bank is active cannot be read with any known read-only query, IMM architecture 3.2.

Additional status words:

  • PLANNED marks an action described but not executed (for example the firmware update plan).
  • NOT VERIFIED / NOT TESTED marks something that would need a test that has not been run.
  • STATE-CHANGING marks a command or capture that changes the machine; read-only marks one that does not. The tools guide uses these words for every command.
  • Derived numbers (arithmetic from documented values) say "derived" and keep the level of their inputs.

How to use them: build on DOCUMENTED and EXTRACTED facts; treat MEASURED values as true for the reference unit at the capture date and as an example for other machines; treat CANDIDATE as a hypothesis to verify; never act on UNKNOWN.

Generations matter #

The x3650 M3 uses the first-generation IMM ("IMM v1", firmware builds named YUOOxxx). Later System x servers use IMM2 (M4/M5 generation, builds 1AOO/TCOO) and then XClarity Controller. Commands, settings, ports and defaults differ between them. The volumes import nothing from IMM2 or XCC without marking it, and several vendor sources (for example S-027, an IMM2 configuration guide) are used only for their explicit IMM1 notes (IMM interfaces 1). The same caution applies to error codes: the dotted UEFI event ids (I.xxxxx, W.xxxxx) of later servers do not exist on this machine (Error codes 6).

Other references you will see:

  • Firmware package paths, for example firmware/ibm/uefi/1.22-d6e164a/, always with SHA256 in a SHA256SUMS file next to the package and a download record in firmware/ibm/SOURCE.txt or the per-package SOURCE.txt of the Lenovo tree.
  • Capture files under captures/, named <date>_<subject>.txt. The public library describes them only generically.
  • Section references such as "STOR 7.1" or "IMMA 3.2" use the abbreviations of the knowledge base index; in this library they are links.
  • Conflict ids (C-1, D-3, SC-2, T-6 ...) are local to the volume that owns them; the index lists them by topic.

Page numbers #

Vendor PDFs have printed page numbers that differ from the PDF page index. Each volume states its convention in its first section. Two common offsets: S-004 printed page = PDF page minus 18; S-020 printed page = PDF page minus 8 (IMM architecture 1, Error codes 1).

How measurements were made #

All MEASURED facts come from one reference unit and were captured with commands that read state without changing it:

  • in-band IPMI over the KCS interface with ipmitool (sensors, SDR, SEL, FRU, LAN and SOL configuration),
  • display-only commands of the IMM legacy CLI (vpd, syshealth, ifconfig, users, ssl, readlog ...),
  • OS-side inventory (dmidecode, lspci, lsusb, ACPI tables, /proc and /sys, EFI variables, smartctl),
  • storcli show commands for the RAID controller, run from a temporary copy and removed afterwards,
  • ASU show all over KCS, and the parameterless "Get" operations of the IMM WS-Management and CIM interfaces,
  • network service discovery of the IMM (port scans, SLP discovery, protocol probes).

A small number of captures record configuration changes that the owner requested (for example creating a virtual disk or enabling serial console redirection). Those are explicitly labelled STATE-CHANGING in the volumes and are not presented as observations of an untouched machine. No firmware was flashed, no IMM was reset and no log was cleared to produce any fact in this library.

How firmware was analysed #

Vendor packages (IMM, UEFI, DSA, RAID, HBA and NIC firmware) were downloaded from IBM and Lenovo, hashed and then analysed offline as untrusted data:

  • the project's own parsers (scripts/ibm_fw_unpack.py, scripts/uefi_fv.py, scripts/imm_upd.py) read bytes and write extracted copies to a scratch directory; they never execute anything from a package,
  • Python was run in isolated mode (python3 -I) so that files inside a package cannot be imported,
  • results (module lists, setup forms, ASU setting tables, microcode lists, file system contents, version strings) are recorded with the package SHA256 and the command used (Firmware formats 9).

The library publishes analysis and metadata only, not the vendor binaries (see About).

Limitations #

  • One machine. Measured values come from a single unit with a sparse configuration (one CPU, one DIMM). Fan speeds, power readings, sensor sets and PCIe topology will differ on other configurations.
  • Firmware gaps. The IMM 1.30 image installed on the reference unit was not obtainable, so IMM internals are EXTRACTED from 1.10 and 1.55 images and only bracketed (CANDIDATE) for 1.30 (Firmware formats 7.8).
  • Static analysis only. Behaviour that can only be seen by running an update, resetting the IMM or rebooting is marked NOT VERIFIED; the update plan in the volumes is PLANNED and was deliberately not executed.
  • Withdrawn product. Some vendor pages are gone (for example the ServerProven list, S-037); some downloads need an IBM ID. Gaps are recorded as UNKNOWN rather than filled from memory.
  • Conflicting sources. Vendor documents disagree in places (maximum memory, memory speed at two DIMMs per channel, part numbers, remote-presence resolution). Both values are kept; see Knowledge base 4.1.
  • Not advice. Guides describe what the documents and analysis show. They are not a recommendation to change a particular machine; flashing firmware or changing settings carries the risks described in the firmware guide.
