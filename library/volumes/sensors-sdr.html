Scope: decode of every sensor that the IMM (v1, build YUOOC7E, IPMI firmware 1.30) of the owner's server exposes in its sensor data record (SDR) repository: name, sensor number, sensor type, event/reading type, entity ID/instance, unit, thresholds (lnr/lc/lnc/unc/uc/unr), measured value and state; fan and cooling zones; meaning of the discrete states; links to IMM event IDs and light path LEDs; abnormal readings, contradictions and the read-only captures that would close the gaps. Generation: IMM v1 (not IMM2/XCC). Rules: docs/AGENT.md.

Offline compilation: no command was run against the server, the IMM or the internet for this document. All MEASURED values come from the captures listed in section 1 (taken 2026-10-19 and 2026-10-20). The full verbose SDR dump of 2026-10-20 (C-V) is tabulated in section 13.

Conventions:

  • Truth levels: DOCUMENTED, EXTRACTED, MEASURED, CANDIDATE (reason given), UNKNOWN. A table states its level; rows inherit it unless a cell says otherwise.
  • Hex values: 0x... ipmitool prints entity IDs in decimal ("29.1" = entity 29 = 0x1D, instance 1); this document gives both forms. ipmitool prints sensor numbers of full records as "32h" = 0x32.
  • "Event ID" = the IMM event ID format AABBCCDD-EEFFxxxx of docs/X3650M3_ERROR_CODES.md section 3: BB = event/reading type, CC = offset, DD = sensor type, EE = entity ID, FF = entity instance. That field decode is CANDIDATE (ERROR_CODES Q-03); the IDs and messages themselves are DOCUMENTED (S-004).
  • Sensor type, reading type and entity of a discrete sensor in sections 7.1-7.7 were first taken from the S-004 event IDs that name the sensor ("catalog-derived", CANDIDATE). Since 2026-10-20 the verbose dump (C-V, section 13) gives sensor number, entity and sensor type of every sensor as MEASURED; it agrees with every catalog-derived value (section 13.2). ipmitool -v does not print the event/reading type code of a discrete record; it is inferred from the offset names that ipmitool prints (for example "Transition to OK" = severity 0x07), which stays CANDIDATE.
  • IPMI v2.0 offset tables (section 6) are quoted from knowledge of the specification, which is not in sources/ (ERROR_CODES Q-03); they are CANDIDATE, and each offset used for a decode is cross-checked against the S-004 message text for the same offset where the catalog has one ("corroborated").

3.3 Discrete sensor columns #

For a discrete sensor ipmitool sensor prints | 0x<reading> | discrete | 0x<b1><b2> |. On this capture the reading column equals the first state byte in all 117 readable discrete rows (e.g. 0x1 / 0x0180, 0x40 / 0x4080, 0x80 / 0x8080, 0x2 / 0x0280) - MEASURED. Interpretation (CANDIDATE, IPMI v2.0 Get Sensor Reading response from knowledge, not in sources/): b1 = state bits for offsets 00-07 (bit n = offset n asserted), b2 = offsets 08-0E with bit 7 reserved and returned as 1 - which explains why every b2 reads 0x80 (MEASURED). So:

Raw (b1b2) Asserted offset(s)
0x0080 none
0x0180 00
0x0280 01
0x4080 06
0x8080 07
na no reading returned (sensor not scanning / entity absent)

Averaging window, AC/DC basis and accuracy: UNKNOWN - the IMM I User's Guide 6th ed. (47c9202) has no power-metering section, and the Linux ibmaem documentation (https://docs.kernel.org/6.8/hwmon/ibmaem.html) only says AEM v1 reports average power over a configurable interval; IMM 1.14 YUOO73M "Improved the accuracy of power readings on x3650 M3" (IMM 1.55 .chg). 13.2 Comparison with the catalog-derived values of section 7 #

  • Sensor type: every catalog-derived sensor type in sections 7.1-7.7 equals the C-V sensor type (MEASURED comparison). Sensors without a catalog entry now have MEASURED types: DASD Backplane 1-4 Entity Presence (0x25), Aux Log System Event (0x12), Progress System Firmwares (0x0F), SEL Fullness Event Logging Disabled (0x10).
  • Entity: the catalog EE byte equals the C-V entity ID for every sensor. The FF byte equals the C-V instance for physical entities (fans, front panel, risers, CPU 1/2, DIMM n, PS n, drives, PCI 1-5, system board, BIOS, IOH, watchdog, NMI). For group or logical entities the catalog FF byte equals the C-V instance with bit 7 set: Power Unit and Host Power 19.1 vs 13/81; All CPUs, One of The CPUs, CPUs, CPU Fault Reboot 37.4 vs 25/84; All DIMMS, One of the DIMMs, DIMMs, Backup Memory 37.1 vs 25/81; PCIs, All PCI Error, One of PCI Error 37.2 vs 25/82; Cooling Zone n 30.n vs 1E/8n. CANDIDATE: the IMM event ID sets bit 7 of the instance for these entities (reason: consistent over 16 sensors in 5 entity groups; no source defines the event ID instance field, ERROR_CODES Q-03). This replaces the single-sensor note on Power Unit in section 2.1.
  • Asserted states agree with the CANDIDATE decode of section 7 wherever both exist (e.g. CPU 1 "Presence detected" = offset 07; DIMM 3 "Presence Detected" = offset 06; DASD Backplane 2 "Absent" = offset 01; Cooling Zones "Fully Redundant" = offset 00); ipmitool's decoding uses the IPMI tables built into ipmitool, so this corroborates but does not raise the section 6 offset tables to DOCUMENTED.
  • PCI 1-5 share entity 48.1 (0x30/01) and differ only by sensor number (0xC4-0xC8), consistent with the single catalog ID 806f0021-3001 for all five.

13.3 Raw SDR dump 2026-10-21 (MEASURED) and firmware SDR files (EXTRACTED) #

Source: captures/2026-10-21_sdr_raw_dump.txt (ipmitool sdr dump in-band, read-only; 8010 bytes; hex dump, offline decode of every record, comparison with the IMM firmware SDR files in build/, extracted with scripts/ibm_fw_unpack.py).

  • Record types: 229 = 13 full (01h) + 122 compact (02h) + 24 FRU locator (11h) + 1 MC locator (12h) + 8 entity association (08h) + 61 OEM (C0h). ipmitool prints the first four kinds (160 lines); the last two are the 69 unprinted records of section 2.1.
  • OEM records: manufacturer ID 0x004F4D = 20301 (IBM), sub-type 0xED, each naming one light-path LED: Fault, Info, CPU, PS, DASD, FAN, DIMM, NMI, OVER SPEC, TEMP, SP, Identify, PCI, CPU 1-2, FAN 1-3, DIMM 1-18, Channel A-E, CNFG, LOG, RAID, Planar, Riser 1-2, Battery, PCI 1-4, SAS MISSING, SAS ERR, BRD, VRM, LINK, BMC Heartbeat, Power (plus two 0xEE records). The list equals, name for name and in order, the WS-Man GetVirtualLightPath list (captures/2026-10-21_imm_wsman_read_inventory.txt). The inner field layout is undocumented.
  • Entity associations: cooling unit 30.n contains fan 29.n (n = 1..3: each "Cooling Zone n" is exactly one fan module); power unit 19.1 contains power supplies 10.1-10.2; group entity 0x25 instance 1 contains DIMMs 32.1-32.16, instance 3 drive bays 4.0-4.11, instance 4 processors 3.1-3.2, instance 2 entity 0x30 instance 1.
  • Raw fields not printed by ipmitool -v: init flags 0x7F (full) / 0x67 (compact); discrete reading masks (used in SC-3, SC-6, SC-9); logical entity instances stored with bit 7 set (Power Unit and Host Power 19.0x81, group entity 0x25.0x8n), which is why the IMM event IDs carry 81/8n (section 13.2 CANDIDATE now MEASURED at the SDR level); conversion factors, e.g. Planar VBAT M=127, R exponent -4 (0.0127 V/count; lc raw 0xA5 = 2.0955 V, lnc raw 0xB1 = 2.2479 V), fan tachs M=29 ("A") / M=25 ("B") RPM per count, Avg Power M=10 W, Altitude M=40 ft, Ambient Temp M=1 B=-132.
  • Platform: the IMM selects its SDR file per platform. IMM 1.55 etc/vpd_list maps VPD 0x0050 / POS 0x0002 to vpd-highvol.sh, which picks victory_ref when the riser-type GPIO reads 0 and the planar ID is 4 (destiny/destiny_ref for the other riser type). The FRU 0 Board Extra values 0002 and 0050 of this server equal that POS/VPD pair (CANDIDATE meaning of those fields). Name-set comparison against all 30 platform files of IMM 1.55: best match var/bmc/victory_ref/victory_ref.sdrdat (EXTRACTED).
  • Identity: 228 of the 229 live records are byte-identical to the IMM 1.55 victory_ref file; the only difference is Planar VBAT -> CMOS Battery (section 8). Against IMM 1.10 victory_ref, 1.30 adds PS 1/2 OP Fault, adds offset 06 to the Power Supply n masks (0x000B -> 0x004B) and offset 03 to the DIMM masks (0x00B2 -> 0x00BA), and sets bit 7 on the Power Unit / Host Power instances. So an IMM update from 1.30 to 1.55 changes only the battery sensor and adds three sensors (EXTRACTED).
