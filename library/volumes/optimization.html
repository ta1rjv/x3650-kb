1. Summary and priority list #

The machine is a single-socket Xeon E5606 (4 cores, no Turbo, no Hyper-Threading) with one 8 GB DIMM on one of three memory channels, booting Proxmox from a RAID0 virtual disk on a single 14173-hour SATA HDD behind a cacheless ServeRAID M1015 in the ICH10 x4 slot. Its firmware is from 2011 (IMM 1.30, UEFI 1.13 build D6E154A) and the CPU runs microcode 0x14. The biggest levers are therefore hardware and firmware, not kernel knobs.

Priority (CANDIDATE ranking; reasoning in the referenced sections):

5. CPU: operating mode, P-states, C-states, Turbo, Hyper-Threading #

5.1 What the CPU can and cannot do #

  • Turbo: the E5606 has none (DOCUMENTED S-001; MEASURED no ida flag). The UEFI items "Turbo Mode" (uEFI.TurboModeEnable) and "Turbo Boost" (uEFI.TurboBoost) therefore have no effect on this CPU (CANDIDATE: firmware cannot enable a feature the part lacks; consistent with the absent flag). Do not spend a reboot on them.
  • Hyper-Threading: none (DOCUMENTED + MEASURED). uEFI.ProcessorHyperThreading is irrelevant on this CPU.
  • P-states (EIST): present and active; OS range 1197-2128 MHz (MEASURED). With no Turbo, the highest P-state is the nominal 2.13 GHz (CANDIDATE: the 2128 MHz cpufreq maximum equals the nominal frequency within rounding).
  • C-states: the OS uses intel_idle with POLL, C1, C1E, C3 and C6, all enabled and all used; C6 holds 95.9 % of the idle time of cpu0 (MEASURED, C-W2). CANDIDATE: intel_idle drives these states from its own per-model table, so their use does not prove the live UEFI "CPU C State" value (reason: agent knowledge of the driver, not verified on this host). The UEFI 1.22 setup XML defaults are uEFI.ProcessorCcxEnable ("CPU C State") = Disable and uEFI.PackageCState = ACPI C2 (greyed out while CcxEnable is Disable); uEFI.ProcessorC1eEnable = Enable (EXTRACTED, docs/X3650M3_UEFI.md section 7). The live values of the installed build D6E154A are UNKNOWN (needs ASU, section 13).

Assessment for this machine (CANDIDATE, reasoning given):

  • Performance mode disables P-states and C1E and enables a Turbo the CPU does not have. The only remaining effect is pinning the cores at 2.13 GHz all the time, which the OS can already do with the performance governor. Expected gain: none in throughput, possibly lower wake-up latency; cost: higher idle power. Not recommended.
  • Efficiency and Acoustic modes lower QPI and memory speed settings. Memory already runs at the E5606 limit of 1066 MHz; whether "Power Efficiency" or "Minimal Power" drops it further (for example to 800 MHz) is UNKNOWN. On a memory-starved single-channel host this is a risk for VM performance. Not recommended without a measurement.
  • Custom mode (the default and, per the help text, the only mode in which the individual questions are editable) is the recommended mode. Within Custom: keep P-states Enable, C1E Enable, memory and QPI at Max Performance, and enable C-states (R-C5).

5.3 C-states and the firmware-update erratum #

  • S-022 p.10 (DOCUMENTED): "Due to an Intel erratum, if your server is running Linux or VMware, you should disable C-States before you update UEFI, IMM, FPGA, or DSA Preboot. C-states can be returned to the original settings after the updates are complete. See RETAIN TIP H195678." Updates through the IMM web or CLI interface do not have this requirement. The IMM 1.55 README restricts it to 32-bit Linux command-line updates (conflict, section 14).
  • Consequence: if C-states are enabled (R-C5), any in-band (Proxmox-side) firmware update must be preceded by disabling them again, or the update must be done through the IMM web interface.
  • Expected benefit of enabling C-states: lower idle power on a host that measured 80 W at capture time (CANDIDATE; reason: S-035 describes C-states as halting the core clock in idle and C1E as an automatic voltage/frequency reduction; the size of the saving on this machine is not measured). Expected cost: small wake-up latency (CANDIDATE, S-035 C-state text). No number is claimed.

6. Memory #

6.1 Current state and the cost of it #

One 8 GB RDIMM in DIMM03 uses one of the CPU's three DDR3 channels (MEASURED + DOCUMENTED, docs/X3650M3_MEMORY.md sections 3, 9). Two consequences (CANDIDATE, from the topology): memory bandwidth is limited to one channel, and 7.7 GiB is the total for host, ZFS ARC (if a pool exists), KSM and all guests.

6.2 Rules that apply (DOCUMENTED, docs/X3650M3_MEMORY.md sections 5, 6, 11) #

  • Speed = min(CPU limit, DIMM rating, DPC limit). The E5606 limit is 1066 MHz (S-001 model 7945-22x row). 1 DPC and 2 DPC give 1066 MHz on this CPU under both S-001 and S-002; 3 DPC gives 800 MHz.
  • Fill order per CPU for performance: 3, 6, 9 (one DIMM per channel), then 2, 5, 8, then 1, 4, 7. Connectors 10-18 need the second CPU.
  • RDIMM and UDIMM never mixed. 1.5 V and 1.35 V RDIMMs may be mixed on Xeon 5600; all then run at 1.5 V.
  • Mirroring needs identical pairs (3+6 first), sparing needs three identical DIMMs (3, 6, 9).
  • After any DIMM change: disconnect power, wait 10 seconds; refit the DIMM air baffle.

6.4 CPU swap as a memory and compute upgrade (hardware, CANDIDATE option) #

10.2 Why the UEFI update matters for a KVM host #

  • Microcode in UEFI (EXTRACTED, docs/X3650M3_UEFI.md section 9): 0x206C2 is 0x15 in UEFI 1.14 and 0x1F (2018-05-08) in 1.22; the OS runs 0x14 (MEASURED).
