1. Scope and conventions #

  • Truth levels (docs/AGENT.md): DOCUMENTED (vendor document), EXTRACTED (firmware binary), MEASURED (capture from the owner's server), CANDIDATE (inference, reason given), UNKNOWN.
  • Page convention: pN = PDF page index of the file under sources/text/ (form-feed count). For S-020 the printed page number is the PDF page minus 8 (for example PDF p43-44 = printed 35-36). S-022 printed = PDF page. S-002: printed = PDF page minus 14 (J147 Table 5 PDF p43-45 = printed 29-31). S-004: printed = PDF page minus 18 (J147 Table 4 PDF p37-38 = printed 19-20). Other documents (docs/X3650M3_SYSTEM_ARCHITECTURE.md) cite S-002 and S-004 by printed page; convert with these offsets. S-025 is a .doc without a text file; it was read by strings extraction from sources/pdf/S-025_transitioning_to_uefi_and_imm.doc and is cited by section number.
  • S-021 (6th edition, May 2013) is essentially identical to S-020 (First Edition, Feb 2015, Lenovo-branded) for every point cited here; S-020 is cited.
  • Generation rule: only IMM v1 facts are used. IMM2/XCC behavior is not imported. S-027 (IMM1 vs IMM2 ASU settings) is used only for its IMM1 notes.
  • Credentials are never recorded. The documented factory default login exists in S-020 p33-34 but is not reproduced here and is not present on this unit (MEASURED, captures/2026-10-19_imm_cli_baseline.txt).
  • Captures referenced are under captures/ with the prefix 2026-10-19_ (imm_cli_baseline, ipmi_inband, nmap_tcp, nmap_udp, nmap_ssh, nmap_tls, tls_openssl, imm_web, snmp, lanoverusb_host, os_inventory, hw_lspci_*, hw_lsusb_v, hw_resources), plus captures/2026-10-20_imm_readlog.txt (imm_readlog, IMM event log, "#N" = entry index, 1 = newest) and captures/2026-10-20_imm_cli_settings.txt (cli_settings, display-only CLI reads of 2026-10-20 ~18:05 IMM clock; values in docs/X3650M3_IMM_INTERFACES.md 4.2).
  • Everything here was produced offline from repository material; nothing was run against the server or IMM.
  • Verification pass 2026-10-20: facts re-checked against the captures, sources/text/ pages, the IMM 1.55 README/changelog and a fresh offline unpack of the UEFI 1.14 package (same SHA256 as below); corrections are in place in the text. nmap rule interpretation (5.3, 5.4) uses the local nmap 7.80 data files (/usr/share/nmap/nmap-payloads, nmap-service-probes), the same nmap version as the captures.

3. IMM v1 internals #

3.1 Integration and SoC #

  • DOCUMENTED: the IMM combines service processor functions, a video controller and (with the optional Virtual Media Key) remote presence in a single chip (S-020 p19, printed 11; S-020 p9 adds Super I/O to the list). S-001 p8: Matrox G200eV with 16 MB memory integrated into the IMM. S-002 p21: video controller integrated into the IMM. S-024 p4 (diagram): the IMM contains BMC, RSA, SIO, SPI+flash, TPM, USB and video functions.
  • MEASURED (hw_lspci_tvnn, hw_lspci_vvv): the IMM is attached behind ICH10 root port 00:1c.4 as PCI device 06:00.0 "Vitesse Semiconductor VSC452 [SuperBMC]" (PCI ID 101b:0452, subsystem IBM 1014:0369, PCI Express to PCI/PCI-X bridge, x1 2.5 GT/s). Behind it, 07:00.0 is the Matrox MGA G200EV (102b:0530, subsystem 1014:0369, 16 MB prefetchable BAR, host driver mgag200). Bridge windows: memory 97000000-978fffff, prefetchable 96000000-96ffffff.
  • The identification as a "SuperBMC" comes from the PCI ID only (MEASURED). EXTRACTED from the IMM 1.10 images of Lenovo DS109380 (docs/X3650M3_FIRMWARE_FORMATS.md section 7, captures/2026-10-21_imm_upd_1.10_analysis.txt s5-s8): the firmware is big-endian MIPS32 (uImage arch MIPS, ELF "MIPS32 MSB"); kernel and bootfs drivers are named vsc452 (vsc452-nand, vsc452_spi, vsc452 gpuart, vsc452_mem/_i2c/_gpio/_pwm/_timer.ko), consistent with the VSC452 PCI ID (CANDIDATE that this is the SoC); U-Boot prints "Clock set to 300MHz" and "Available RAM set to 112M / 48M / 24M" (selection logic UNKNOWN); spiutil knows the SPI flash parts MX25L12805D and S25FL128P. The installed 1.30 image itself is still not available (IBM Fix Central requires an IBM ID).
  • EXTRACTED for IMM 1.55 (YUOOH5A, FORMATS 7.9, captures/2026-10-21_imm_upd_1.55_analysis.txt): the same embedded OS evolved - Linux 2.6.16.46-377 (built 2017-12-21), U-Boot 1.1.4 (2018), same uClibc 0.9.29 and JFFS2 layout. Userland bumped where it matters: OpenSSL 0.9.8a -> 1.0.2d and libcurl 7.44.0; OpenSSH 4.2p1, lighttpd 1.4.13, vsftpd 2.0.4, BusyBox 1.4.2 and OpenSLP 1.2.1 stay (security fixes backported, no version bump). 1.55 adds BIND 9.3.4 (named/DDNS), a strongSwan+pluto/racoon IPsec stack, Cyrus SASL 2.1 and Berkeley DB 4.3 that 1.10 lacks. The x3650 M3 platform profile (lib/libvictory_ref.so) is still present, so 1.55 serves this machine. Since these component versions are unchanged from 1.10, the installed 1.30 ships the same versions and lacks the 1.44-1.55 OpenSSL/OpenSLP fixes (CANDIDATE, bracketed by 1.10 and 1.55).

3.2 Flash and banks #

  • DOCUMENTED: the IMM has a primary and a backup (secondary) firmware ROM page. Jumper J147 "IMM recovery": pins 1-2 (normal) boot the primary IMM ROM page, pins 2-3 boot the secondary (backup) page; with no jumper the board behaves as 1-2 (S-002 PDF p43-45 = printed 29-31, Table 5; S-004 PDF p36-38 = printed 18-20, Table 4). Jumper J29 "UEFI boot recovery": pins 2-3 select the backup UEFI ROM page. Do not change the jumper position after the server is turned on (S-004 PDF p38 = printed 20, note 2, written for the UEFI boot recovery jumper). This resolves the "jumper UNKNOWN" item in docs/X3650M3_FIRMWARE_HISTORY.md.
  • DOCUMENTED: flash packages offer --backup; README of IMM 1.55 sections 2.1.1 and 2.4.3: "Target the secondary/alternate flash bank if available. If a alternate device is not supported, the IMM may ignore this option." The iflash64 binary (EXTRACTED, below) and S-023 use the wording "Target the secondary flash device if available."
  • DOCUMENTED: IMM 1.40 (YUOOF7A) "Enabled IMM to fail over to backup automatically when there is a IMM firmware corruption" (changelog, firmware/ibm/imm/1.55-yuooh5a/*.chg). IMM 1.07 (YUOO48E) "Changed the firmware to light the Information LED if the primary UEFI bank becomes corrupted" (same changelog). S-004 event 806f052b-2101xxxx is "IMM FW Failover" (PDF p174, printed 156); 40000023/40000024 are flash success/fail (PDF p68, printed 50); 4000002a is a firmware mismatch (PDF p70, printed 52).
  • DOCUMENTED (IBM RETAIN tip H206034, https://www.ibm.com/support/pages/node/860842, read 2026-10-21): with IMM 1.30 (YUOOC7E, the build installed here), 1.31 or 1.32 the IMM can reset unexpectedly, fail over to the alternate bank and, if that bank fails to initialize, stop working; AC cycling does not recover it; fixed in 1.33 (YUOOE3C). Flashing 1.30-1.32 onto a bank recovered at 1.29 or older also fails. The tip lists only BladeCenter HX5 and x3690/x3850/x3950 X5 as affected configurations, not the x3650 M3 7945: applicability to this server is CANDIDATE (reason: same IMM1 build ID YUOOC7E). Implication: any IMM flash or reset here carries a non-recoverable risk until a recovery path exists; no SPI flash part number or external-programmer procedure for the 7945 was found.
  • DOCUMENTED (UEFI side, S-024 p17-18): UEFI has dual banks with automatic bank recovery driven by IMM watchdogs (power-sequence watchdog; POST watchdog disabled by default). The IMM switches primary to backup; restore by updating the primary, rebooting once on backup, then AC cycle for 15 s or F3 at the splash screen.
  • DOCUMENTED (S-024 p15, S-025): UEFI settings live in two tiers, UEFI NVRAM variables and XML-modeled settings stored in IMM NVRAM; IMM settings are on the IMM file system and reachable by ASU.
  • MEASURED (UEFI side, os_inventory SMBIOS type 11 OEM strings): the server runs from the primary UEFI bank; primary D6E154A (reported as 1.13), backup bank D6E154A. See section 2.
  • EXTRACTED (IMM 1.10, FORMATS 7.3; applicability to 1.30 CANDIDATE): the IMM firmware lives on NAND managed by UBI with two sides: kernel in UBI volumes 1/2, rootfs in 3/4, bootfs in 7/8 (etc/init.d/rfs.mirror:60-74, ifs.mtd-stage2:22 "Customer layout contains two rootfs copies in volumes 3 and 4"). U-Boot sits at offset 0 of an IMM SPI flash; its environment variable bootvolume (read with spiutil env ibmc -r bootvolume) selects the side, and U-Boot's bootbmc boots "from either primary or secondary UBI volumes. If neither is valid, attempt to tftp the image" (BOOTVOL/BADVOL flags). An update writes the inactive side only (libfmp_ibmc: "/dev/mtd3 mounted, programming ubi0_2, ubi0_4"), and rfs.mirror later copies the running side to the other with ubimirror. This is the software view of the "primary/backup ROM page" above; how J147 maps to bootvolume is UNKNOWN.
  • EXTRACTED (captures/2026-10-21_imm_rootfs_unknown_extracts.txt U-098): in 1.10 rfs.mirror runs every minute from etc/cron.minute and, after a flash, copies the running side to the other side, so both sides end up with the same build. 1.55 has no rfs.mirror (ubimirror is only used by the bin/testfix script); its libfmp_ibmc sets bootvolume and clears badside1/badside2/flipside after programming the inactive side, i.e. the previous build stays as the fallback. Which model 1.30 follows is UNKNOWN; with the 1.10 model the backup side would also hold YUOOC7E (CANDIDATE). Live: CIM_SoftwareIdentity lists only IMM, UEFI and DSA, and Tasks/GetFirmwareBuildID faults for every FirmwareType including "backup" (MEASURED, captures/2026-10-21_imm_cim_read_inventory.txt, captures/2026-10-21_imm_wsman_firmware_buildid.txt).
  • EXTRACTED (IMM 1.10): the IMM can read and write the host UEFI SPI flash directly (spiutil raw bios -r/-w, libfmp_ibmc "Burning new layout"; YUOO57X burn.sh writes 0x380000-0x7DFFFF of a dx360 M2 UEFI flash, FORMATS 7.6). The x3650 M3 offsets are UNKNOWN.
  • UNKNOWN: which IMM bank is active, the IMM backup bank firmware level, whether jumper J147 is in the default position, the exact NAND and SPI parts fitted on this board. No read-only query was found; update and flash commands are forbidden on this host (docs/AGENT.md).

3.3 Boot, heartbeat, recovery #

  • DOCUMENTED: IMM heartbeat LED flashes fast while IMM code loads and slowly when fully operational; if it is not flashing within 30 s of AC connection, a trained technician uses the IMM recovery jumper and then replaces the board (S-004 PDF p41, printed 23). The power button becomes active about 2 minutes after AC is applied (S-020 p19). Resetting the IMM via the setup utility takes about 4 minutes (S-020 p125). DSA IMM I2C test note: disconnect AC for 45 s to reset the IMM (S-004 PDF p310, printed 292).
  • DOCUMENTED: configuration backup excludes the Security page settings (S-020 p94) and the SSH server private key (S-020 p92); restore defaults then restart IMM (S-020 p25, p95-96).
  • DOCUMENTED: in IMM1, changes to the network settings (for example IMM.HostName1, IMM.SharedNicMode, IPv4 settings) take effect after the next IMM restart, while IMM2 applies them immediately (S-027 p19-20, "Difference from IMM1" notes). S-020 p50: network protocol changes require an IMM restart.

4. Host interfaces #

4.1 KCS / IPMI (system interface) #

  • MEASURED (os_inventory SMBIOS type 38): interface type KCS, IPMI spec 2.0, I2C slave address 0x10, NV storage not present, base I/O address 0xCA2. /proc/ioports shows 0ca2 and 0ca3 owned by ipmi_si (hw_resources.txt lines 157-162); /dev/ipmi0 exists. The kernel log uses slave address 0x20 (8-bit form of the SMBIOS 0x10; see docs/X3650M3_SYSTEM_ARCHITECTURE.md section 7).
  • MEASURED (ipmi_inband mc info): supports Sensor Device, SDR Repository, SEL, FRU Inventory, IPMB Event Receiver and Generator, Chassis. "Provides Device SDRs: no". mc getsysinfo and dcmi discover fail with "Invalid command" (not implemented).
  • MEASURED: mc getenables shows SEL logging enabled and event message buffer enabled. Chassis power restore policy: previous.
  • MEASURED: 13 IPMI user slots reported; channel 1 is 802.3 LAN, IPMB-1.0, multi-session, protocol vendor ID 7154 (meaning not established in sources).
  • In-band access from the Proxmox host: ssh root@[lab-ip] ipmitool ... (docs/AGENT.md).

4.2 LAN over USB #

  • DOCUMENTED: an internal virtual Ethernet link between IMM and host OS ("Commands on USB interface", enabled by default) used for in-band ASU and firmware flash (S-020 p32, p129-131; S-022 p8, p11). Disable via web "Allow commands on USB interface" or CLI usbeth -en disabled (S-020 p32, p150). Disabling affects ASU and in-band flash, not remote presence USB devices. UEFI path: System Settings > Integrated Management Module > Commands on USB Interface Preference (S-022 p8; same item name in the UEFI setup tree, docs/X3650M3_UEFI.md).
  • DOCUMENTED addresses: IMM 169.254.95.118/255.255.0.0 (S-020 p129, S-025 section 8.2.1), secondary node of a multi-node system 169.254.96.118 (S-020 p129); Linux host static 169.254.95.130/255.255.0.0 (S-020 p131, S-025 section 8.2.1). The IMM may choose another 169.254.x.x address on collision (S-025 section 8.2.1). See conflict 1 in section 12 for other host-side values.
  • DOCUMENTED: IMM 1.15 and later runs a DHCP server on this link (S-022 p9; cdc_interface.sh 0.9.0). Note: the IMM 1.55 changelog has no 1.15 release (1.14 YUOO73M is followed by 1.16 YUOO73O); conflict 14.
  • Drivers: Linux usbnet + cdc_ether; Windows RNDIS INF (ibm_rndis_server_os.inf plus device.cat in the packages).
  • MEASURED (lanoverusb_host): USB device 04b3:4010 "IBM RNDIS/CDC ETHER", bcdDevice 2.15, two configurations (1 = CDC Ethernet, 2 = RNDIS), "Self Powered" in both configuration descriptors (device status reads "Bus Powered"), MaxPower 100 mA, wMaxSegmentSize 1514, full speed (12M) on bus 5 port 2 (UHCI 00:1d.0, hw_lsusb_v), driver cdc_ether, interface enx5ef3fce08adf in state DOWN with no address, route or neighbors. The host side is therefore not configured, and the IMM DHCP behavior at 1.30 was not exercised (live test = host network change, not done). IMM side: usbeth -en enabled (MEASURED, cli_settings line 26).
  • EXTRACTED (1.55 etc/usb0_refresh.sh, captures/2026-10-21_imm_rootfs_unknown_extracts.txt U-039): the IMM runs dhcpd on usb0 with subnet 169.254.(95+node).0/24 and a single-address range .120-.120, and sets its own usb0 to 169.254.(95+node).118/16; node 0 gives IMM .118 and host .120. The 1.10 image has no such files (no DHCP server). S-022 dates the DHCP server to 1.15, so 1.30 CANDIDATE has the 1.55 behavior.
  • MEASURED: no virtual keyboard, mouse or storage USB device from the IMM is present. CANDIDATE: those appear only with the Premium key and an active remote presence session. MEASURED 2026-10-21: no remote presence license (GetKVMStatus HasLicense 0, MaxSessions 0, section 7), so the key is not active.

4.3 Video and remote presence #

  • DOCUMENTED: remote presence supports up to 1280x1024 at 75 Hz (S-001 p28; S-020 p15 table 1, p113; S-021 p113), 15-bit color depth, USB 2.0 virtual keyboard/mouse/mass storage, absolute and relative mouse, Java Plug-in 1.5+ or ActiveX on Internet Explorer; IE 6/7/8 and Firefox 1.5+ listed (S-020 p15-16). Port 3900 carries remote presence (S-020 p44). S-002 and S-004 give 1600x1200 at 75 Hz for remote viewing instead (conflict 2).
  • MEASURED: host-side graphics is Matrox G200EV behind the IMM bridge (section 3.1).

4.4 Serial and SOL #

  • DOCUMENTED (S-020 p16, p41): COM1 = IPMI serial-over-LAN, configurable only through IPMI; COM2 = serial redirection through Telnet/SSH (internal on rack servers, not IPMI-configurable); 8N1, 9600-230400 baud. S-002 p32: the rear serial port is shared with the IMM.
  • MEASURED (ipmi_inband): SOL enabled, force encryption true, force authentication false, privilege USER, 115.2 kbps, payload port 623.

4.5 Other host-visible items #

  • DOCUMENTED: OS watchdog and loader watchdog (server timeouts) require the in-band USB interface; the IMM restarts the server on a missed check (S-020 p29); if the USB in-band interface is disabled, the watchdog timeouts should also be disabled to prevent unexpected restarts (S-020 p32, p129).

  • DOCUMENTED: password authentication only, no public-key authentication; key generation creates RSA and DSA keys for SSH v2 (S-020 p92). Telnet and SSH sessions use the legacy CLI.

9. Update flow #

9.1 Order and prerequisites #

  • DOCUMENTED order: IMM, then UEFI, then (FPGA, not present on this server), then DSA Preboot (README 1.4; S-022 p11-12). IMM must be 1.07 or later before UEFI/DSA updates (README 1.4); the changelog header says 1.14 or later (conflict 13; the installed 1.30 satisfies both). Updating to IMM 1.30 requires a current level of 1.10 (YUOO57H) or later, otherwise "the system will not power on correctly" (fixed in 1.31) (README 1.4/changelog). After downgrading from 1.22 to an earlier version the IMM must be reset to factory defaults (changelog header); 1.09 to 1.10 enforces alpha and numeric passwords or may need a reset to defaults (changelog); moving from below 1.05 to 1.05 or later reverts alert recipient e-mails and DST (README, S-022 p9). When down-levelling below 1.07 from 1.07/1.08, AC power must be removed before a server reboot (README 1.2).
  • Intel C-state erratum: README 1.4 says 32-bit Linux (command-line updates); S-022 p10 says Linux or VMware. Updates through AMM, BoMC or the IMM web/CLI are not affected (both).
  • Never power off during "Secure Region Update in Progress" (CRTM update after a UEFI update, S-022 p10). Updates with BoMC, UXSPI, AMM or in-band individual packages take at least 17 minutes (S-022 p9).

9.2 Methods #

  • UpdateXpress System Pack Installer / Bootable Media Creator preferred (S-022 p6).
  • Web interface: Firmware Update, then Restart IMM; UEFI and DSA updates need the server powered on and no IMM restart (S-020 p123-124).
  • CLI: update -i <TFTP_IP> -l <file> (S-020 p153).
  • Flash package: <package>.bin -s, -x <path> to extract, iflash options --package --user --password --unattended --force --backup --no-reboot --silent (README); iflash64 strings additionally show --reboot, --tftp [port], --disable-imm-lan, --kcs and a password-file option (EXTRACTED).
  • In-band updates need LAN over USB enabled and drivers; if disabled, use the web update (S-022 p8, p11; S-020 p32, p129). Windows: when the current IMM is below 1.12, updating to 1.14-1.30 adds up to 10 minutes and to 1.30 or later up to 20 minutes of iflash pre-check wait (changelog header).
