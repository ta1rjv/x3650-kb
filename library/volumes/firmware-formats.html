Command: python3 -I scripts/ibm_fw_unpack.py info <package> (EXTRACTED).

Layout: [stub executable][unzip helper][image.tar][image.zip][imgboot.cfg][20-byte trailer]. The trailer is five little-endian uint32 values: stub size, unzip size, image.tar size, image.zip size, imgboot.cfg size.

Contents (EXTRACTED via ibm_fw_unpack.py extract):

  • image.tar: oem_ibm.xml (2206 B, flash descriptor, section 5) and <build>.tar.gz (1995822 B for d6e156b, mtime 1328204274 = 2012-02-02; 1954061 B for d6e164a, mtime 1528128550 = 2018-06-04). The tarball holds the five UEFI images and is what the .upd carries.
  • image.zip: wrapcfg (x86/x64 sections), image/ with c_state_fix.sh, cdc_interface.sh, device.cat, ibm_rndis_server_os.inf, iflash, iflash.exe, iflash64, iflash64.exe, readme.lin, readme.win, plus the wrapper executable (linwrap in 1.14, winwrap.exe in 1.22). The rndis files support the LAN-over-USB interface to the IMM (cdc_interface.sh, device.cat, inf).
  • wrapcfg keywords seen: dialogTitle "IBM uEFI Flash Update", packageType UEFI, packageVersion, packageBuildLevel, two dmiData lines "s0.5 D6" and "s0.5 -[D6" (both present in 1.14 and 1.22), matchCmdLine such as "./iflash64" --package ibm_fw_uefi_d6e156b-1.14_anyos_i386.upd --force, usageCmdLine --pkgsdkhelp, extractHD 6. The 1.22 gui_options expose --backup ("Update Alternate Bank"), --user and --password.
  • imgboot.cfg keys: os_clauses, final_startup_cfg, image_tar_name, startup_cmd (./linwrap or .\winwrap.exe), and an args rule "override <defaultArgs> with <userArgs>".

The dmiData match (DMI string prefix "D6") is how the wrapper checks the package against the machine's current UEFI build identifier; this reading is CANDIDATE (the match logic lives in the wrapper binary, not analyzed).

4. Descriptor files (.xml, .chg, .txt) #

  • .xml (CIM-style descriptor, class IBMPSG_SystemUpdateElement), parsed with python3 -I scripts/ibm_fw_unpack.py xml <file.xml> (EXTRACTED, 1.22 file): Version "Version 1.22 -[D6E164A-1.22]-", SoftwareElementID D6E1, buildNumber D6E164A, ibmSchemaVersion 3.1, releaseDate 20180703000000.000000-300, severity 1, rebootRequired 3, crc 201baf4f (equals the CRC-32 of the whole .exe, verified with zlib.crc32), size 3802 (the .exe is 3802822 bytes, so the unit is 1000 bytes, truncated), preReq ibm_fw_imm_yuoo57h_windows_32-64, unattended command <package>.exe -s. applicableMachineTypes: x3650 M3 (4255, 5454, 7945), x3650 M2 (7947, 3797, 3798, 4199), x3550 M2/M3 (7946, 4198, 3795, 3796, 7944, 4254), Smart Analytics 7949. Operating systems: Windows 2003, 2003 x64, 2008, 2012, 2012 R2. preReq yuoo57h is IMM 1.10 (IMM 1.55 readme section 1.4).
  • .chg: plain-text change history; the 1.22 file carries notes for 1.00 (D6E123A) to 1.22 (used in docs/X3650M3_FIRMWARE_HISTORY.md).
  • .txt: the readme. The 1.22 readme is identical in content to image/readme.win inside the package (DOCUMENTED, vendor readme).

Command: python3 -I scripts/ibm_fw_unpack.py upd build/doc/x22/elements/image.tar (EXTRACTED). The argument is the image.tar file, not a directory.

Flash map as described by the XML (active bank address, EXTRACTED):

File Active address Length
Capsule_P.scap 0x7FFFFFFFFFC40000 0x40000

FvDxe.fv 0x7FFFFFFFFFE00000 0x100000

1.14 differs only in compressed_size 2007040, release_date 02/02/2012, build_id D6E156B and image_version 1.14; in both releases compressed_size equals the size of the package's image.tar element (section 3). Each <file> also carries a volume attribute: for the four .fv files it is the FV name GUID in little-endian byte order (for example 583ff6c8... = C8F63F58-488D-470C-...); for Capsule_P.scap it decodes to 42C47C24-A467-4EB3-995C-BC5FDF315BD9, which is not the inner FV name (CCA16F07-...) and does not occur in the capsule file (meaning UNKNOWN).

The XML also holds a commented/alternate block with the same names at 0xFFFFFFFFFFxxxxxx (backup bank) and savetobackup/restorefrombackup copies of 0x3C0000 bytes between 0x7FFFFFFFFFC00000 and 0xFFFFFFFFFFC00000. The two bank bases are consistent with the primary/backup (ABR) design of S-024 pp.17-18; how the addresses map to the physical SPI flash is UNKNOWN. The descriptor declares size 4194304 (4 MiB) but the listed images and the 0x3C0000 copy region cover less than that; the remainder (for example the locked CRTM region of S-024 pp.17-18) is not described in the package (CANDIDATE).

Details:

  • Capsule_P.scap: capsule header GUID 25b5fe76-8243-4a5c-a9bd-7ee3246198b5, header size 0x1c, image_size 0x3fa3c. A trailer at 0x3f81c of 0x220 bytes carries an EFI_CERT_TYPE_RSA2048_SHA256_GUID (a7717414-...) signature. The inner FV (offset 0x1c, length 0x3F800) holds the early boot code: TrustedCodeUpdateDriver, PeiMain (PEI core), PEIMs (MonoStatusCode, PeiCpuIo, PciCfg, CpuPeim, PlatformInfo, PlatformEarlyInit, SecureCapsule, TrustedCodePei, PlatformKey2, OpPresence, TcgPei), SECURITY_CORE and a nested compressed FREEFORM file (130122 B). This is the "secure/trusted code" region with capsule signature verification of S-024 p.25 (DOCUMENTED); the match of the capsule to that mechanism is CANDIDATE.
  • FvDxe.fv: DXE core (DxeMain), HiiDatabase, UefiPlatform (setup forms), LegacyBios (CSM), IbmIpmiCommands, TcgDxe, SMM drivers, and the 8086:1229 legacy option ROM (56320 B).
  • FvPlatform.fv: Bds, SetupBrowser, SetOptions, SysCfgDrv, PciBus, USB drivers, ACPI tables, option ROMs (Matrox 102B:0530 legacy 32768 B + EFI 20992 B; Broadcom 14E4:1639 BCM5709 legacy 73728 B + EFI 71168 B), Ip4Config, IScsi, PxeConfig.
  • FvOem_Ibm.fv: two BMP logos (1.22: 7bb28b99-... 800x600 8 bpp, 481078 B; ba28b996-... 800x600 24 bpp, 1440056 B; in 1.14 7bb28b99 is 800x600 24 bpp, 1440054 B, and ba28b996 is identical to 1.22), the ASU/setup XML (file GUID 92217677-6658-49ce-8899-a01ec4009790) and the oemIbmMiscSubclass driver.
  • FvMicrocode.fv: one RAW file 197DB236-F856-4924-90F8-CDF12FB875F3 (FFS header at 0x90, body at 0xA8) holding concatenated Intel microcode updates (analysis in docs/X3650M3_UEFI.md).
  • Section compression is the UEFI/Tiano scheme (tool column "tiano"); the tools decompress it themselves.

7. IMM packages (.upd) #

DOCUMENTED only: the IMM 1.55 readme (firmware/ibm/imm/1.55-yuooh5a/) describes the packaging commands: -x <path> extracts, flash options are the same iflash options (section 8), the update order is IMM then UEFI then DSA Preboot (both readmes; S-022 pp.11-12 adds FPGA between UEFI and DSA). Waiting times: at least six minutes after an IMM update before a UEFI/DSA update when not using UXSP, BoMC or the AMM (UEFI 1.22 readme section 1.4); at least fifteen minutes when updating through the AMM (both readmes), ten minutes for IMM 1.09+ with AMM 50L+ (IMM readme); the IMM can take up to 17 minutes to be ready (S-022 p.7; "at least 17 minutes" p.9), while S-022 p.12 says the initial restart after an IMM update can take up to 20 minutes. RETAIN tip H196209 notes that updating UEFI backup firmware with IMM32F may fail (S-022 p.15, list only).

The DOCUMENTED IMM 1.55 readme says nothing about the image layout. The smx-smx "ibmextract" lead is not applicable (DOCUMENTED, source read 2026-10-21): it is an "IBM Power Server update extractor" for big-endian POWER .pak packages (https://github.com/smx-smx/tools/tree/master/ibmextract). A 2026-10-21 search found no public unpacker or signing description for IMM1 "yuoo" packages; the two .upd files below came from Lenovo DS109380 (firmware/lenovo/management-module-imm-imm2-amm-cmm-smm/DS109380/, SOURCE.txt) and were analyzed offline on 2026-10-21 (nothing executed, no IMM contact). 12.4 Changes 2.1.5b -> 2.4.1c relevant to the 5709 #

  • 2.1.5b .chg history for 7945: 2.1.1c "Added support for ... 7944 and 7945"; 2.1.3b and 2.1.5a "Changes were made to the NCSI code for ... 7945" (no details; it refers to change-history zips that are not local). 2.1.5b itself only "Added iSCSI config update support for mfg" with no firmware change (DOCUMENTED).
  • Net version deltas (from 12.3): bootcode 5.2.2 -> 7.4.0, NC-SI 2.0.10 -> 2.0.13, MBA 5.2.7 -> 7.8.75, iSCSI boot 4.2.12 -> 7.10.4, IPMI unchanged 1.0.1 (EXTRACTED). The content of these changes is UNKNOWN.

NC-SI and the IMM: S-002 (Figure 9 text) says that with the Ethernet 1 connector "the network can be shared with the IMM through a single network cable" and S-021 offers a dedicated or shared IMM connection (DOCUMENTED). The 5709 runs NC-SI management firmware (MEASURED: "NCSI 2.0.11"), and the IBM package ships NC-SI, not IPMI/UMP, for 7945 (DOCUMENTED). That the shared IMM mode uses NC-SI over this 5709 as sideband is CANDIDATE (consistent, but no source states it for the x3650 M3). The owner's IMM uses the dedicated port (docs/X3650M3_SECURITY_REVIEW.md).

12.5 How the update tool flashes (EXTRACTED from strings; DOCUMENTED from the .txt) #

  • README (.txt sections 1.2, 2.0): needs bnx2 >= 1.6.6b (tg3 >= 3.58b for NX1), ports up with an IP address on each port, libstdc++.so.5/6; run ./brcm_fw_nic_<version>_linux_32-64.bin -s (silent); it updates only if the installed level is lower; -force overrides the version check. RHEL5 Xen is not supported (use BoMC).
  • Chain: PKG SDK stub (unpacks into a directory ibm_ux_pkg_<hex>, under /tmp CANDIDATE; runs /usr/bin/unzip or its own miniunz) -> linwrap -> ./install.sh -> fwuplnx -> backend lnxfwnx2 for NetXtreme II through libbmapi (in-band over the bnx2 driver, OS online). fwuplnx strings show backend calls of the form %s %s upgrade -noreset -F -%s %s nv.bak and cfg -mgmt, cfg -ipmi 0, cfg -ump 0, cfg -asf 0, cfg -mfw_wol_speed 5, and a log in /var/log/IBM_Support/ (brcmfwup.log). The nv.bak argument suggests an NVRAM backup before upgrade (CANDIDATE).
  • fwuplnx usage (strings): -v (display installed versions), -s, -nomfw (disable management firmware on all NICs), -ncsienable, -ncsidisable, -crc, -f; hidden -force, -iscsicfgupdate, -iscsicfgversion, -nxncsi, -dir. -nomfw/-ncsidisable would cut a shared IMM link (CANDIDATE).
  • Extract without flashing: linwrap usage strings offer -x <dirname> ("Extracts contents to <dirname>") and wrapcfg sets extractHD 1, so -x is enabled for this package (EXTRACTED, not executed). Static carving with unzip <package>.bin (it skips the 74943-byte prefix) or python3 -I scripts/ibm_fw_unpack.py extract works without running anything (EXTRACTED, done for this analysis). Running fwuplnx -v on the host would read the installed MBA/iSCSI levels, but that runs vendor code with NVRAM access and needs owner approval.
