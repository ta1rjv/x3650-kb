Engineering reference for the web interface of the owner's IMM (first-generation IMM, firmware 1.30, build YUOOC7E, machine 7945KEG) and the WS-Management API that the web client uses. 1. Overview, sources and conventions #

1.1 What this document covers #

  • The IMM 1.30 web UI is a frameset application written in JavaScript. Almost every page reads and writes IMM state through WS-Management custom operations: the client downloads six WSDLs at login and turns every WSDL operation into a global JavaScript function top.<Operation>(input, callback) (EXTRACTED, home_imp.js:161-231).
  • Besides /wsman, the client uses a small set of plain HTTP endpoints for the session (/session/*), file transfer (/br/*, /certs/*, /spevents.elg), the KVM launcher (/kvm/*) and a few helpers (section 4.4).

  • EXTRACTED: read directly from a file served by the IMM firmware and stored in the repository (UI code and the WSDL documents). The UI code is part of the firmware image, so its content is treated like extracted firmware content. EXTRACTED states what the client code does or what the WSDL declares, not what the server enforces.
  • MEASURED: observed in a live capture (HTTP headers, SLP replies, SOAP response headers, ASU output).
  • DOCUMENTED: vendor document, cited through docs/X3650M3_IMM_INTERFACES.md where the citation already exists.
  • CANDIDATE: inference, with the reason given. UNKNOWN: not established.
  • "NOT TESTED" marks request shapes in section 9 that were never sent. Values quoted from wsread are MEASURED; the meaning of a numeric code is EXTRACTED when a stored UI file maps it to a display text (file:line given), otherwise the raw value is given and its meaning is UNKNOWN.

2. Server stack #

  • MEASURED: Server: lighttpd/1.4.13 on port 80, 200 OK, text/html, 3616 bytes, Last-Modified: Fri, 30 Sep 2011 07:37:35 GMT, ETag: "-1747512116" (imm_web lines 8-15). The 3616-byte body is index.html (CRAWL line 1: GET index.html 200 3616).
  • MEASURED: the WS-Man endpoint is served by the same web server under /wsman: every WSDL GetResponse carries <wsa:From><wsa:Address>http://[lab-ip]/wsman</wsa:Address></wsa:From> and a uuid: MessageID (WSDL, Header of each file). EXTRACTED: the client builds the endpoint as <scheme>://<host>/ + wsman (home_imp.js:51).
  • CANDIDATE: the session, backup/restore and WS-Man handlers are lighttpd plugins (modules) rather than CGI programs. Reason: client comments "Since lighttpd plugin is single threaded, the response of that request will come only after the backup file response is received" (impl/ibmccontrol_configfile_imp.js:86-89), the callback name recvLightyLogin for /session/activate (home_imp.js:471-475), "response from lighttpd contains an extra html content after plugin specific error" (impl/ibmccontrol_restoremodify_imp.js:2040), and no cgi path in any client URL (the crawler excluded paths containing "cgi" but none was referenced, CRAWL).
  • MEASURED: the CIM server is a different process: Server: sfcHttpd on 5988, 501 Not Implemented for GET and OPTIONS, 401 with WWW-Authenticate: Basic realm="cimom" for a CIM-XML POST; 5989 closed (cim lines 5-49). SLP names it "Small Footprint CIM Broker 1.2.5" (slp line 49).

3. UI architecture #

3.1 Frames and page loading #

  • EXTRACTED: / (index.html, internally named home.html) is a frameset: frameHeader (55 px row), and below it a column set frmSet with frameTree and frameMain; all three start as page/blank.html (index.html:82-88). frmSet.cols is "0," (tree hidden) during login and "200," once logged in (home_imp.js:501-509).
  • EXTRACTED: the top window loads lib/eExt.js, lib/wsman/wsman.js, lib/eLang.js, str/EN/global_str.js and home_imp.js (index.html:39-51). The comment at index.html:41-45 states the design: the WS-Man library is loaded in the top window so the operation functions it creates are reachable from every lower page.
  • EXTRACTED: content pages live in page/*.html and include their logic from impl/<page>_imp.js plus lib/ui.js, lib/eLang.js and lib/pageinc.js (for example page/monitors_systemstatus.html:30-39). Pages call operations as top.<Operation>({...}, recv); several pages use tables of function references with invokeGetOperations (lib/ui.js:549) and a page-local invokeSetOperations (impl/ibmccontrol_systemsettings_imp.js:48, impl/ibmccontrol_networkprotocols_imp.js:59), for example impl/ibmccontrol_systemsettings_imp.js:104-124 and 175-200.
  • EXTRACTED: lib/pageinc.js polls GetAssertedEvents 3 s after each page load to update the status icon (lib/pageinc.js:8, 23) except on login/session/logoff/locked/upload-failure pages (lib/pageinc.js:15-20).
  • EXTRACTED: localisation strings come from str/<lang>/*.js; only str/EN/global_str.js was stored. Page-specific string files such as navobj_str.js and session_str.js are written by document.write at run time (page/frameTree.html:44, page/session.html:32) and were not fetched by the crawler.
  • EXTRACTED: the client targets Firefox and Internet Explorer and logs an error for other browsers (lib/wsman/wsman.js:164-183).

4. Login and session flow (static client code) #

Described from the client code only. No credential was used for this document. The only authenticated interaction recorded in the repository is the owner-approved WSDL download of 2026-10-20 (README.md section "wsdl/"), which used the same /session/create, WS-Transfer Get and /session/deactivate requests described here.

4.1 Sequence #

The comment at home_imp.js:25-33 lists the steps: login page, create session, load WSDLs, check password, session page, main page. In detail (all EXTRACTED):

  1. doInit (home_imp.js:45-92): sets wsmanURI (51); takes a session id from the URL fragment #sessionid:<id> (53-58) or the session_id cookie, where the value none means no session (60-62). With a session it reloads the WSDLs and opens the main frame; otherwise it loads page/login.html (84-88). It also requests GET /hostname.txt?time=<ms> for the window title (102-104).
  2. Login form: two text inputs _txtiUsername and _txtiPassword and a button _btnLogin; there is no HTML form element (page/login.html, line 16, form commented out). startLogin rejects an empty user name and calls top.login(user, password) (impl/login_imp.js:38-51).
  3. login sends POST /session/create with the raw body <user>,<password> (comma-separated, no encoding, no extra header) (home_imp.js:348-353). Response handling (home_imp.js:356-402):
    • body starting with ok: authenticated. If the browser did not receive a usable session_id cookie, the client takes resp.substr(3) as the session id, stores it in top.gSessionID and in the URL fragment (365-372). CANDIDATE: the body is ok plus one separator character plus the id; the separator is UNKNOWN.
    • unauthorized: alert, form cleared (385-392); locked: page/locked.html (394-397); existing: page reload (398-401).
  4. The client loads the six WSDLs one after the other (home_imp.js:376-382, 161-194; section 5.3).
  5. GetPasswordStatus (home_imp.js:236-266): Status 1 = expired, 2 = required -> page ibmccontrol_loginchangepwd.html, BlankPasswordAllowed decides whether an empty new password is accepted (234-235, 247-251). ChangePassword sends Using: "1" ("changing via PAM") and NewPassword (268-271).
  6. Otherwise UserLogOniBMC with DestIPAndPort: "[<hostname>]:<port>" and LogInForcefully: "0" (home_imp.js:255-261). The response gives UserLogOniBMCResponse (0 = success), SessionTimeout, UserIDAndIP, SystemName, DisplayName (300-324; WSDL Monitors message UserLogOniBMCResponse). The user name is stored in a username cookie when the cookie session is in use (318-320).

5. WS-Man client #

5.1 Transport (EXTRACTED) #

  • Endpoint: POST <scheme>://<host>/wsman (home_imp.js:51, 207). The WSDL soap:address is the literal "No Target Adress" in every WSDL (WSDL, element service/port), so the client overrides it with wsmanURI.
  • HTTP headers: Content-Type: text/xml, Connection: close (lib/wsman/soap.js:64-66), plus session_id when the header session is used (lib/wsman/network.js:31-34) and optionally NoSessionUpdate: yes. No SOAPAction header is sent (the code is commented out, lib/wsman/WSDLOperation.js:150-154).
  • XMLHttpRequest is asynchronous; timeout 5 * 3600 * 1000 ms, i.e. 5 hours, although the comment says 5 minutes (lib/wsman/network.js:12); up to 2 retries for HTTP status codes outside 200, 400, 401, 403, 405, 415, 404, 500 (lib/wsman/network.js:13-15, 66-71).
  • HTTP 400 and 500 responses are parsed as SOAP faults (lib/wsman/soap.js:109-113).

5.2 Envelope shape (EXTRACTED, lib/wsman/soap.js:213-276, lib/wsman/WSDLOperation.js:22-146) #

Namespaces (lib/wsman/XML.js:19-27): SOAP-ENV = http://www.w3.org/2003/05/soap-envelope, wsa = http://schemas.xmlsoap.org/ws/2004/08/addressing, wsman = http://schemas.dmtf.org/wbem/wsman/1/wsman.xsd. Header elements in this order: wsa:To (endpoint), wsa:ReplyTo/wsa:Address (anonymous role), wsman:ResourceURI, optional wsman:SelectorSet with wsman:Selector name="..." (lib/wsman/soap.js:424-438), wsa:Action, wsa:MessageID = dt:<milliseconds>. Body: one element named after the operation with xmlns = the WSDL soap:body namespace (lib/wsman/wsdl.js:171-173), and one child per input part; simple parts carry xsi:type="xsd:<type>" (WSDLOperation.js:139-144), complex parts are built from the WSDL schema.

Generic custom-operation request as the client builds it (structure EXTRACTED; values are placeholders):

<SOAP-ENV:Envelope xmlns:SOAP-ENV="http://www.w3.org/2003/05/soap-envelope"
    xmlns:wsa="http://schemas.xmlsoap.org/ws/2004/08/addressing"
    xmlns:wsman="http://schemas.dmtf.org/wbem/wsman/1/wsman.xsd">
  <SOAP-ENV:Header>
    <wsa:To>http://<IMM>/wsman</wsa:To>
    <wsa:ReplyTo><wsa:Address>http://schemas.xmlsoap.org/ws/2004/08/addressing/role/anonymous</wsa:Address></wsa:ReplyTo>
    <wsman:ResourceURI>http://www.ibm.com/iBMC/sp/<Service></wsman:ResourceURI>
    <wsa:Action>http://www.ibm.com/iBMC/sp/<Service>/<Operation></wsa:Action>
    <wsa:MessageID>dt:<ms></wsa:MessageID>
  </SOAP-ENV:Header>
  <SOAP-ENV:Body>
    <Operation xmlns="http://www.ibm.com/iBMC/sp/<Service>"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:xsd="http://www.w3.org/2001/XMLSchema">
      <SimplePart xsi:type="xsd:int">0</SimplePart>
    </Operation>
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>
  • Resource URI = the service namespace without a selector: createOp binds every operation to the resource URI it was loaded from and passes selectorSet = null (home_imp.js:213-224). The action URI comes from the portType input wsa:Action attribute (lib/wsman/wsdl.js:189), which in every WSDL is http://www.ibm.com/iBMC/sp/<Service>/<Operation> (WSDL, portType).
  • The client accepts only rpc/encoded operations (lib/wsman/WSDLOperation.js:24-25); all six WSDLs declare style="rpc" and use="encoded" (WSDL, binding).
  • Response: the first child of the SOAP Body is the operation response; its children are mapped by part name to a JavaScript object, and the part count must equal the WSDL output message (lib/wsman/WSDLOperation.js:181-201). Many Set operations return an int where "0" is success and "-1" failure (lib/pageinc.js:71-72).
